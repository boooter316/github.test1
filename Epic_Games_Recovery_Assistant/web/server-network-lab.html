DigitalOcean — create your own VPS

  1. Create an account and enable multi-factor authentication.
  2. Generate an SSH key on your Windows PC; upload only the public key to DigitalOcean. Keep the private key on your device.
  3. Create a Droplet using a supported Ubuntu LTS image and a size appropriate for your workload.
  4. Choose a datacenter region near your users. Record the Droplet's assigned public IPv4/IPv6 address in your own password manager or infrastructure notes.
  5. Attach a Cloud Firewall: allow SSH (TCP 22) only from your current trusted admin IP; open only the application ports you actually need.
  6. Connect using SSH, update packages, create a non-root administrator, configure unattended security updates, and verify backups.
  7. Enable monitoring and alerts. Review billing and destroy unused Droplets.
Do not paste API tokens, passwords, private SSH keys, or recovery codes into this page or GitHub. The project does not provision cloud resources or store DigitalOcean credentials.

Official guides: Create a Droplet · Cloud Firewalls · Connect with SSH.

Private VPN — WireGuard planning

  1. Use a VPS you control and install WireGuard from the distribution's supported packages.
  2. Generate separate key pairs for the server and each device. Private keys remain on their respective devices.
  3. Assign a small private tunnel subnet and document each peer's allowed addresses.
  4. Configure the host firewall to permit the chosen WireGuard UDP port only as needed; keep SSH restricted to your admin IP.
  5. Enable IP forwarding and NAT only if you intentionally want the VPN to route traffic through the VPS.
  6. Install the official WireGuard client on each device, import that device's configuration securely, and test DNS, routing, and reconnect behavior.
  7. Revoke lost-device peers immediately and rotate keys if a private key may have been exposed.
A VPN does not make activity anonymous or authorize access to systems you do not own. Do not use VPN routing to evade bans, conceal attacks, or relay harmful traffic.

Private proxy — safe design

A proxy can be useful for testing your own web applications or routing traffic inside a private environment. Design it as a restricted service, not an open proxy.

  • Choose a maintained proxy implementation and follow its official hardening guide.
  • Bind the listener to a private interface or VPN address rather than all public interfaces.
  • Require strong authentication and encrypt the client-to-proxy connection.
  • Use firewall allow-lists so only your own devices or private subnet can connect.
  • Apply connection limits, logging appropriate to your privacy policy, patching, and abuse monitoring.
  • Test from an authorized client and confirm that unauthenticated external clients cannot relay traffic.
This project intentionally does not generate an open-proxy deployment script, proxy chains, rotating residential proxies, or traffic-concealment tooling.

For general network concepts, see MDN: Proxy servers and tunneling.

Kali Linux — authorized learning environment

  1. Download the official VirtualBox image or installer from Kali's website.
  2. Verify the published checksum/signature before importing the image.
  3. Use a dedicated VM with a non-sensitive snapshot and NAT networking by default.
  4. Update the VM after first boot and use a standard user account for daily work.
  5. Practice only against intentionally vulnerable lab targets or systems for which you have written permission.

VirtualBox — install and configure

  1. Check that hardware virtualization (Intel VT-x / AMD-V) is enabled in firmware.
  2. Install VirtualBox from the official download page for your host operating system.
  3. Create a Linux VM with resources appropriate to your computer; avoid allocating all host RAM or CPU cores.
  4. Use NAT for ordinary internet access. Use host-only networking for isolated lab communication; avoid bridged mode unless you understand the exposure.
  5. Take a clean snapshot before experiments and keep shared folders/clipboard disabled unless needed.
  6. Install Guest Additions only from trusted official sources when required.

PuTTY — SSH to your own VPS

  1. Install PuTTY from its official website.
  2. In DigitalOcean, copy the Droplet's public IP address from its dashboard.
  3. Open PuTTY, enter that IP as the Host Name, choose SSH, and keep port 22 unless you intentionally configured another port.
  4. Under Connection → SSH → Auth, select your private key file if using key authentication. Never upload or share that private key.
  5. Connect and verify the host-key fingerprint against a trusted provider console or first-connection record.
  6. Sign in with the non-root account you created. Close the session when finished and keep SSH firewall access restricted.
Use SSH for normal server administration only. This guide does not configure C2, remote implants, command beacons, or unauthorized remote control.

PuTTY official download and documentation.

Installation requirements checklist

  • Windows 11 or another supported host OS with current security updates.
  • Hardware virtualization enabled; enough free disk space, memory, and CPU capacity for a VM.
  • VirtualBox and the official Kali Linux image, checksum verified.
  • PuTTY or another maintained SSH client.
  • DigitalOcean account with MFA and a billing method, if you choose to rent a VPS.
  • SSH key pair, public key uploaded to the VPS provider, private key stored securely on your PC.
  • Firewall rules, patching, backups, monitoring, and a documented recovery path.
  • WireGuard client/server packages only if you choose to create a private VPN.
  • A private proxy implementation only if your use case requires one; authentication and firewall restrictions are mandatory.

No cloud account, paid Droplet, VPN subscription, proxy service, or VM is created automatically by this guide. Review current provider pricing and system requirements before installing.
